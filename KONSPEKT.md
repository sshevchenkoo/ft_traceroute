## 1. Что делает traceroute

Нужно узнать, через какие роутеры проходит пакет до цели. Прямого способа спросить об этом у сети нет, поэтому traceroute использует поле **TTL** (Time To Live) в IP-заголовке:

- каждый роутер уменьшает TTL пакета на 1;
- если TTL стал 0, роутер **уничтожает пакет** и отправляет отправителю ICMP **Time Exceeded** (type 11, code 0). Источник этого ICMP-пакета — адрес роутера.

Если отправлять пакеты с TTL = 1, 2, 3, ..., то ответит сначала первый роутер, потом второй и так далее:

```
TTL=1  ──► [R1] TTL→0, drop ──► ICMP Time Exceeded от R1     хоп 1 = R1
TTL=2  ──► [R1] ──► [R2] drop ──► ICMP Time Exceeded от R2     хоп 2 = R2
TTL=3  ──► [R1] ──► [R2] ──► [цель] UDP на закрытый порт
                                 ──► ICMP Port Unreachable      дошли, стоп
```

**Как понять, что дошли.** Классический Linux traceroute (и наш) отправляет **UDP на заведомо закрытый порт**: 33434, и +1 для каждого следующего зонда. Цель не слушает этот порт и отвечает ICMP **Destination Unreachable, code 3 (Port Unreachable)**. Получив такой ответ, трассу заканчиваем.

> **33434** = 32768 + 666. Это «высокий порт, который вряд ли кто-то слушает». Значение пришло из оригинального traceroute Van Jacobson (LBL, 1987).

На каждый хоп отправляется **3 зонда** (probes), поэтому в строке три времени. Максимум **30 хопов**, ответа ждём не больше **5 секунд**. Всё это значения по умолчанию у оригинального traceroute.

## 2. Протоколы

### 2.1 IPv4-заголовок (`struct ip`, `<netinet/ip.h>`)

```
 0       4       8              16                              31
+-------+-------+---------------+-------------------------------+
|Version|  IHL  |      TOS      |          Total Length         |
+-------+-------+---------------+---+---------------------------+
|        Identification         |Flg|      Fragment Offset      |
+---------------+---------------+---+---------------------------+
|      TTL      |   Protocol    |        Header Checksum        |
+---------------+---------------+-------------------------------+
|                        Source Address                         |
+---------------------------------------------------------------+
|                     Destination Address                       |
+---------------------------------------------------------------+
|                    Options (если IHL > 5)                     |
```

Что из этого нужно нам:

| Поле | В `struct ip` | Зачем |
|---|---|---|
| IHL | `ip_hl` | длина заголовка в 32-битных словах. **×4 = байты**. Обычно 5 (20 байт), но с опциями бывает больше, поэтому нельзя хардкодить 20 при разборе |
| TTL | `ip_ttl` | им мы управляем при отправке |
| Protocol | `ip_p` | 1 = ICMP, 17 = UDP |
| Source | `ip_src` | кто прислал пакет. Мы берём адрес из `recvfrom`, это то же самое |

### 2.2 UDP-заголовок (8 байт)

```
+----------------+----------------+
|  Source Port   |   Dest Port    |
+----------------+----------------+
|     Length     |    Checksum    |
+----------------+----------------+
```

Наш пакет = 20 (IP) + 8 (UDP) + 32 (данные) = **60 байт**. Отсюда «60 byte packets» в заголовке вывода.

### 2.3 ICMP (`struct icmp`, `<netinet/ip_icmp.h>`)

Заголовок 8 байт: `type`, `code`, `checksum` и 4 байта, которые у сообщений об ошибках не используются.

**Главное, что нужно понимать:** в ICMP-ошибку (Time Exceeded, Dest Unreachable) роутер вкладывает **IP-заголовок нашего исходного пакета и первые 8 байт его данных**. Это RFC 792. Для UDP эти 8 байт как раз весь UDP-заголовок, с нашими портами. Так мы и понимаем, на какой зонд пришёл ответ.

Что возвращает `recvfrom` на raw ICMP сокете:

```
+------------------+-------------+--------------------+---------------+
| внешний IP hdr   | ICMP hdr 8B | внутренний IP hdr  | UDP hdr 8B    |
| ip_hl*4 байт     | type, code  | ip_hl*4 байт       | sport | dport |
+------------------+-------------+--------------------+---------------+
  src = роутер/цель                 = копия НАШЕГО      sport = наш сокет
                                     заголовка          dport = номер зонда
```

### 2.4 Коды ответов и что печатается

| Ответ | type/code | Что делаем | Печать |
|---|---|---|---|
| Time Exceeded in transit | 11 / 0 | промежуточный хоп, идём дальше | адрес и время |
| Port Unreachable | 3 / 3 | **дошли до цели**, стоп | адрес и время |
| Net unreachable (и 6, 8, 11) | 3 / 0 | стоп | `!N` |
| Host unreachable (и 7, 12) | 3 / 1 | стоп | `!H` |
| Protocol unreachable | 3 / 2 | стоп | `!P` |
| Fragmentation needed | 3 / 4 | стоп | `!F` |
| Source route failed | 3 / 5 | стоп | `!S` |
| Administratively prohibited | 3 / 9, 10, 13 | стоп | `!X` |
| Host precedence violation | 3 / 14 | стоп | `!V` |
| Precedence cutoff | 3 / 15 | стоп | `!C` |
| другой code Unreachable | 3 / N | стоп | `!<N>` |
| Time Exceeded, другой code | 11 / 1 | стоп | `!<11-1>` |
| нет ответа за 5 с | — | — | `*` |

Таблица один в один взята из `parse_icmp_res()` оригинального traceroute. Правило оригинала: **любой ответ, кроме Time Exceeded/TTL, финальный.**

## 3. Сокеты

В программе два сокета (`src/init.c`, `open_sockets`):

### 3.1 Отправка: обычный UDP-сокет

```c
socket(AF_INET, SOCK_DGRAM, IPPROTO_UDP);
setsockopt(fd, IPPROTO_IP, IP_TTL, &ttl, sizeof(ttl));   // перед каждым sendto
```

- IP- и UDP-заголовки, а также чексумму собирает **ядро**. Мы только задаём TTL через `IP_TTL`.
- Сокет **bind'ится на порт 0**: ядро выбирает свободный порт, а `getsockname()` сообщает нам, какой именно. Этот порт будет в каждом ответе (внутренний UDP sport), и по нему мы отличаем свои пакеты от чужих. Ядро гарантирует, что порт занят только нашим сокетом, поэтому две копии ft_traceroute, запущенные параллельно, не перепутают ответы.

### 3.2 Приём: raw ICMP-сокет

```c
socket(AF_INET, SOCK_RAW, IPPROTO_ICMP);
```

- Обычный UDP-сокет **не видит** ICMP-ошибки (без `IP_RECVERR`). Raw-сокет получает копию **каждого** входящего ICMP-пакета, **вместе с IP-заголовком**.
- Нужен **root** (или capability `CAP_NET_RAW`): raw-сокет позволяет читать чужой ICMP-трафик и подделывать пакеты, поэтому обычному пользователю он запрещён. Без sudo программа выдаст `socket: Operation not permitted` и код выхода 1.
- Так как приходят *все* ICMP (ping-ответы, ответы чужим traceroute), **фильтрация обязательна** (см. `match_probe`).

> **Как оригинал обходится без root:** он не открывает raw-сокет, а включает на UDP-сокетах `IP_RECVERR` и читает ошибки из очереди ошибок сокета (`recvmsg(MSG_ERRQUEUE)`). Это Linux-специфика. Raw-сокет — классический и более наглядный способ.

### 3.3 Блокирующий режим и `select()`

Сабджект запрещает `O_NONBLOCK`. Сокеты остаются блокирующими, а таймаут делается через `select()`:

```c
FD_ZERO(&rfds); FD_SET(recv_fd, &rfds);
ret = select(recv_fd + 1, &rfds, NULL, NULL, &timeout);
// ret == 0 -> таймаут, ret > 0 -> есть пакет, recvfrom не заблокируется
```

`select` ждёт, пока на сокете появятся данные или истечёт `timeout`. Если `select` сказал «готово», `recvfrom` вернётся сразу. Это не неблокирующий режим, флаг сокета мы не меняем.

| `src/receive.c` | чтение и разбор ICMP, сопоставление с зондом |

### 4.2 Поток выполнения

```
main
 ├─ parse_args      --help / ошибки / host
 ├─ resolve_host    getaddrinfo → dest, dest_ip
 ├─ open_sockets    raw ICMP + UDP (bind :0 → sport)
 ├─ print_header    "traceroute to X (ip), 30 hops max, 60 byte packets"
 └─ run_trace
     loop:
       fill_window     дослать зонды, пока в полёте < 16
       expire_probes   просроченные (>5 с) → done (будет *)
       wait_packet     select до ближайшего дедлайна → receive_packet
       пока хоп ttl полностью done → print_hop, ttl++
```

### 4.3 Данные

```c
typedef struct s_probe {
    struct timeval sent;      // когда отправили
    struct timeval recv;      // когда получили ответ
    int            done;      // есть ответ ИЛИ таймаут
    int            answered;  // есть ответ (иначе печатаем *)
    struct in_addr from;      // кто ответил
    char           err[16];   // "!H", "!X", ... или ""
    int            final;     // этот ответ заканчивает трассу
} t_probe;
```

`t_trace` содержит массив `probes[30 * 3]`, по ячейке на каждый возможный зонд. Структура объявлена `static` в `main`, поэтому она обнулена и лежит не на стеке. **malloc в программе нет вообще**, утечкам взяться неоткуда (valgrind: `All heap blocks were freed`).

**Ключевая идея нумерации.** Зонд с индексом `i` (с нуля):

- TTL = `i / 3 + 1`
- порт назначения = `33434 + i`

Поэтому при получении ответа индекс зонда вычисляется сразу: `dport - 33434`. Никакого поиска и никаких дополнительных таблиц.

## 5. Разбор кода по файлам

### 5.1 `args.c`: аргументы

Сабджект требует поддержать только `--help` и host, а ошибки обрабатывать «разумно». Сообщения скопированы с оригинала, чтобы поведение было как у настоящего traceroute (проверено на `traceroute 2.1.2`):

| Ввод | Вывод (stderr) | Код выхода |
|---|---|---|
| без аргументов | help | 0 |
| `--help` в любой позиции | help | 0 |
| `-x`, `--xxx` | ``Bad option `-x' (argc 1)`` | 2 |
| `--` без хоста | `Specify "host" missing argument.` | 2 |
| `host extra` | ``Cannot handle "packetlen" cmdline arg `extra' on position 2 (argc 2)`` | 2 |
| `a b c` | ``Extra arg `c' (position 3, argc 3)`` | 2 |
| `-` | считается хостом, дальше ошибка резолва | 2 |

Второй позиционный аргумент у оригинала — длина пакета (`packetlen`). Мы её не поддерживаем (сабджект: «solely manage a simple IPv4 host»), поэтому отвечаем той же ошибкой, что оригинал на некорректный `packetlen`.

Разбор идёт в два прохода: `check_options` (опции; `--help` срабатывает, где бы ни стоял, но плохая опция перед ним — ошибка) и `collect_positionals` (позиционные аргументы с их индексами в argv для сообщений).

### 5.2 `init.c`: резолв и сокеты

```c
hints.ai_family = AF_INET;      // только IPv4
getaddrinfo(host, NULL, &hints, &res);
```

- `getaddrinfo` принимает и IP-литерал (`8.8.8.8`), и имя (`google.com`), это и есть «IPv4 address/hostname» из сабджекта.
- `300.1.1.1` не IP и не имя, поэтому ошибка `Name or service not known` (текст даёт `gai_strerror`) и вторая строка как у оригинала, код 2.
- `inet_ntop` переводит адрес в строку для заголовка.
- **FQDN без DNS в хопах.** Имя цели резолвится один раз, а у хопов печатается только IP (никакого `getnameinfo`). Обратный DNS хопов — это бонус «DNS management».

### 5.3 `probe.c`: отправка зонда

```c
ttl = idx / NPROBES + 1;
setsockopt(send_fd, IPPROTO_IP, IP_TTL, &ttl, sizeof(ttl));
dest.sin_port = htons(BASE_PORT + idx);
gettimeofday(&probes[idx].sent, NULL);   // время засекаем прямо перед sendto
sendto(send_fd, data, 32, 0, &dest, sizeof(dest));
```

`htons`/`ntohs` переводят порядок байт (host ↔ network/big-endian). Если `sendto` падает (например, `Network is unreachable` при отсутствии маршрута), печатаем `send: <ошибка>` и выходим с кодом 1. Оригинал выходит с тем же кодом, но пишет `connect: ...`: он делает `connect()` на UDP-сокет, а мы шлём через `sendto()`.

### 5.4 `trace.c`: главный цикл (окно из 16 зондов)

**Почему не «по одному».** Если каждый зонд ждать до 5 секунд по очереди, трасса, которая кончается `* * *` (а это частый случай: многие хосты режут UDP), занимает 30 × 3 × 5 = 450 с. Если слать 3 зонда хопа разом, выходит 30 × 5 = 150 с. Оригинал держит **до 16 зондов в полёте одновременно** (опция `-N`, по умолчанию 16, см. его `--help`), то есть проверяет ~5 хопов параллельно, и такая трасса занимает ~30 с. Мы делаем так же: замер 30 с против 30 с у оригинала.

Алгоритм `run_trace`:

```
ttl = 1                                   // следующий хоп для печати
while ttl <= last_ttl:
    fill_window(first = (ttl-1)*3)        // в полёте (отправлен, не done) < 16?
                                          //   → отправить следующий зонд
                                          //   (но не дальше хопа last_ttl)
    expire_probes                         // у кого прошло 5 с → done (будет *)
                                          // + найти ближайший дедлайн
    if кто-то ждёт и хоп ttl не готов:
        wait_packet                       // select(timeout = до ближайшего дедлайна)
                                          // пришёл пакет → receive_packet
    while хоп ttl готов (все 3 done):
        print_hop(ttl); ttl++
```

Важные моменты:

- **Печать строго по порядку хопов.** Ответ с хопа 5 может прийти раньше, чем истёк таймаут хопа 3, но строка 5 будет напечатана только после строки 3.
- **`last_ttl`.** Изначально 30. Когда приходит финальный ответ (Port Unreachable или `!X`/`!H`/...) от хопа N, `last_ttl = N`. Дальше N мы больше ничего не шлём и ничего не печатаем. Зонды, уже отправленные за N, просто игнорируются.
- **Таймаут считается для каждого зонда отдельно**: `sent + 5 s`. `select` ждёт ровно до ближайшего дедлайна, поэтому, если пришёл «чужой» пакет, мы не начинаем ждать 5 секунд заново.
- **`EINTR`** (прерывание сигналом) у `select` не считается ошибкой: просто идём на следующий круг.

### 5.5 `receive.c`: разбор ответа

`receive_packet`: `recvfrom` → **сразу** `gettimeofday` (точное время приёма, чтобы уложиться в допуск ±30 ms) → `match_probe` → заполнить зонд.

`match_probe` по шагам. Каждая проверка отсекает чужой или битый пакет, и **каждое чтение поля защищено проверкой длины**, чтобы обрезанный пакет не вызвал чтение за границей буфера:

1. Длины хватает на внешний IP + 8 байт ICMP?
2. `type` — Time Exceeded или Dest Unreachable? (Отсекает echo reply и прочее.)
3. Длины хватает на внутренний IP + 8 байт UDP? (Учитываем `ip_hl` **обоих** заголовков.)
4. Внутренний `ip_p == UDP`? (Отсекает ошибки на чужие ICMP/TCP.)
5. Внутренний UDP sport == наш порт? (Отсекает чужие программы.)
6. `idx = dport - 33434` в диапазоне отправленных и зонд ещё не done? (Отсекает опоздавшие ответы на зонды, которые уже напечатаны как `*`.)

Порты читаются через `memcpy` + `ntohs`, а не через поля `struct udphdr`: имена полей этой структуры отличаются в разных версиях glibc (`uh_sport` или `source`), а `memcpy` работает везде и не нарушает выравнивание.

`classify` превращает type/code в метку (`!H`, ...) и флаг `final` (таблица из п. 2.4).

### 5.6 `print.c`: формат вывода

```
traceroute to google.com (142.250.74.46), 30 hops max, 60 byte packets
 1  10.0.2.2  0.512 ms  0.433 ms  0.401 ms
 2  * * *
 3  100.64.0.1  9.871 ms 100.64.0.5  10.002 ms  9.950 ms
 4  10.9.9.9  11.020 ms !H * *
```

Правила (точно как в `print_probe()` оригинала):

- номер хопа `"%2d "`, по правому краю в 2 символа;
- перед адресом **один** пробел, перед временем **два**: `" %s"`, `"  %.3f ms"`;
- таймаут: `" *"`;
- метка ошибки после времени через пробел: `" !H"`;
- **адрес печатается у первого ответившего зонда строки и повторно только если он отличается от адреса предыдущего ответившего зонда** (строка 3: балансировка нагрузки, зонды одного хопа ушли через разные роутеры). Звёздочки при сравнении пропускаются (`must_print_addr`).

**Решение по формату хопов.** Без `-n` оригинал печатает `имя (ip)`, например `_gateway (10.0.2.2)`. Сабджект требует отображать хопы **без DNS-резолва**, поэтому наш вывод совпадает с `traceroute -n`: только IP. С ним и надо сравнивать на защите. Если проверяющий настаивает на формате `ip (ip)`, это правка одной строки в `print_hop`.

## 6. Отличия от оригинала (и почему)

| Что | Оригинал | У нас | Почему |
|---|---|---|---|
| `--help` | все опции | только `--help` | других опций в mandatory нет |
| имена хопов | `name (ip)` | `ip` | сабджект: без DNS в хопах |
| `packetlen` | поддерживается | ошибка | сабджект: только host |
| приём ответов | `IP_RECVERR`, без root | raw-сокет, нужен root | классический способ, проще объяснить |
| адаптивное ожидание (`-w MAX,HERE,NEAR`) | ждёт меньше 5 с, если соседний хоп уже ответил | ровно 5 с | упрощение. На итоговый вывод не влияет, только иногда на время работы |

## 7. Обработка ошибок

| Ситуация | Поведение |
|---|---|
| запуск без root | `socket: Operation not permitted`, код 1 |
| неизвестный хост | `X: Name or service not known` + `Cannot handle "host" ...`, код 2 |
| нет маршрута до сети | `send: Network is unreachable`, код 1 (у оригинала `connect: ...`, код тоже 1) |
| битый/обрезанный ICMP | игнорируется (проверки длины) |
| чужой ICMP-трафик | игнорируется (порт, протокол) |
| сигнал прервал `select`/`recvfrom` | `EINTR`, продолжаем |
| Ctrl+C | стандартное завершение процесса (как у оригинала) |

Сегфолтов быть не может: нет malloc, все буферы фиксированного размера, все чтения из пакета проверены по длине.

## 8. Тестирование

### 8.1 Окружение

- **Защита проходит в Linux VM** (ядро ≥ 4.0, шкала делалась под Debian 7). На macOS код не собирается: `ICMP_TIME_EXCEEDED` и подобные константы есть только в Linux-заголовках.
- В VM ставь сетевой адаптер **Bridged**. VirtualBox NAT часто не пропускает ICMP Time Exceeded, и тогда всё, кроме первого хопа, будет `* * *` даже у настоящего traceroute.
- Эталон: пакет `traceroute` (Dmitry Butskoy), **не** `inetutils-traceroute`, у которого другой формат.

### 8.2 Скрипты в репозитории


Он сравнивает ft_traceroute с `traceroute -n` для всех пяти случаев. Сейчас все совпадают.

## 9. Вопросы на защите (с ответами)

**Почему UDP, а не ICMP Echo?**
Так работает Linux traceroute по умолчанию. UDP на закрытый порт гарантированно вызывает Port Unreachable у цели. ICMP Echo — это `-I` (бонус), `-T` — TCP SYN.

**Зачем каждому зонду свой порт?**
Чтобы сопоставить ответ с зондом: внутри ICMP-ошибки возвращается наш UDP-заголовок, его dport однозначно задаёт индекс зонда → TTL и время отправки.

**Зачем два сокета?**
UDP-сокет удобен для отправки (заголовки строит ядро), но не видит ICMP-ошибки. Raw ICMP-сокет видит все входящие ICMP.

**Почему нужен root?**
`SOCK_RAW` требует `CAP_NET_RAW`: через него можно читать чужой трафик и подделывать пакеты.

**Почему `select`, если O_NONBLOCK запрещён?**
`select` не меняет режим сокета, он лишь ждёт готовности с таймаутом. Когда `select` говорит «готово», блокирующий `recvfrom` вернётся сразу.

**Откуда `* * *`?**
Роутер не отвечает ICMP (политика или файрвол), режет его по rate limit, ответ теряется, либо файрвол цели дропает UDP. Тогда звёздочки до 30-го хопа.

**Почему у одного хопа разные IP в строке?**
Балансировка нагрузки (ECMP): зонды с разными портами хэшируются на разные пути. Это проблема классического traceroute, её решает Paris-traceroute (держит неизменным то, по чему хэширует балансировщик).

**Почему RTT хопа 5 может быть меньше, чем хопа 4?**
Роутеры генерируют ICMP медленным путём (control plane, низкий приоритет), а обратный путь может отличаться от прямого (асимметричная маршрутизация). RTT — время туда и обратно, а не только до хопа.

**Почему 60 байт?**
20 (IP) + 8 (UDP) + 32 (данные), как у оригинала по умолчанию.

**Зачем слать 16 зондов сразу?**
Скорость: таймауты разных хопов идут параллельно. 30 с вместо 150–450 с на трассе со звёздочками. Печать при этом остаётся строго по порядку.

**Что такое ICMP rate limiting и как это видно?**
Ядро Linux (`net.ipv4.icmp_ratelimit`) и роутеры ограничивают частоту ICMP-ошибок. Если два traceroute запустить подряд, второй может получить `*` на хопах, которые только что ответили первому. В тестах из-за этого стоит пауза в 2 с.

**Что будет с `0.0.0.0`?**
Linux трактует его как локальный хост, отвечает `127.0.0.1`. Оригинал ведёт себя так же.

**Что значит IHL и почему не 20 байт?**
У IP-заголовка могут быть опции, тогда длина больше 20. Поэтому смещение до ICMP — `ip_hl * 4`, причём это верно и для внешнего, и для вложенного заголовка.

**Как гарантировано, что нет сегфолта на мусорном пакете?**
Каждое обращение к полю пакета идёт после проверки, что `n` (прочитанная длина) это поле покрывает.

## 10. Требования сабджекта и где они закрыты

| Требование | Где |
|---|---|
| бинарник `ft_traceroute`, C, Makefile (all/clean/fclean/re, без релинка) | `Makefile` |
| только `--help` | `args.c`, `usage.c` |
| IPv4 address/hostname | `init.c`: `getaddrinfo` с `AF_INET` |
| FQDN без DNS в хопах | `init.c` (резолв цели), `print.c` (только IP) |
| ±30 ms | `gettimeofday` прямо у `sendto`/`recvfrom` (`probe.c`, `receive.c`) |
| без O_NONBLOCK | блокирующие сокеты + `select` (`trace.c`) |
| только libc | только стандартные заголовки, без сторонних библиотек |
| не вызывать системный traceroute | только сокеты, никаких `exec`/`system` |
| ошибки без падений | раздел 7 |
| отступы как у оригинала | `print.c`, проверено `tests/` |
